1.目的・背景

IT系講座の課題として、Trello風のタスク管理アプリを個人開発する。目的はツールとしての完成度そのものよりも、要件定義 → 実装 → Gitでのバージョン管理という一連の開発の流れを体験し、身につけることにある。

今回はすでに最小構成(MVP)のプロトタイプを先行して実装済み。本書はその実装内容を振り返って要件として言語化し、今後の拡張の土台とするために作成する。

2.スコープ

対応する範囲と、あえて対応しない範囲を明確にする。3つの固定リストでのタスク管理〜ローカル保存まではv0.1で実装済み。サーバー(DB)へのデータ保存は今後実装予定の範囲として、対応する側に含める。

対応する

  • 3つの固定リスト(未着手/進行中/完了)でのタスク管理
  • カードの追加・削除・編集(テキスト・期限)
  • ドラッグ&ドロップによるリスト間移動
  • 期限に基づく自動並び替え
  • カード内のチェックリスト(小項目)
  • チェックで完了リストへ自動移動、終了日の記録
  • ブラウザ内へのデータ保存(localStorage)
  • サーバー(DB)へのデータ保存(認証なし・単一ユーザー想定)

対応しない(今回)

  • ユーザー登録・ログイン
  • 複数ユーザーでの共有・権限管理
  • 複数ボードの作成
  • リストの追加・編集
  • 同一リスト内でのカードの手動並び替え

3.用語定義

  • ボード
    タスク管理画面全体を指す最上位の単位。今回は1つのボードのみ存在する。
  • リスト
    進捗ステータスごとの列。「未着手」「進行中」「完了」の3種で固定。
  • カード
    1件のタスクを表す最小単位。テキスト・期限・小項目・終了日を持ち、いずれか1つのリストに属する。
  • 小項目
    カードの中にぶら下がるチェックリストの1項目。テキストと完了フラグを持つ(カード自体とは別に完了・未完了を管理できる)。
  • 終了日
    カードが「完了」リストに入った日付。チェックボックスで完了させた日、またはドラッグで完了リストへ移動した日が自動で記録される。

    • 4.ユースケース

    機能要件(5章)を導出する元となる、利用者の行動をユーザーストーリー形式で整理する。「〜として、〜したい、なぜなら〜だから」の形で、各機能要件(REQ)がどの行動から生まれたかを対応づける。

    ID ユーザーストーリー 関連REQ
    UC-01 利用者として、思いついたタスクをすぐに追加したい。なぜなら忘れる前に記録しておきたいから REQ-01
    UC-02 利用者として、不要になったタスクを削除したい。なぜなら一覧を整理された状態に保ちたいから REQ-02
    UC-03 利用者として、タスクの進捗に応じてカードを別のリストへ移動したい。なぜなら今どの段階かひと目で把握したいから REQ-03
    UC-04 利用者として、ブラウザを閉じても入力したタスクが消えないでほしい。なぜなら毎回入力し直すのは非効率だから REQ-04
    UC-05 利用者として、タスクの内容や期限をあとから修正したい。なぜなら予定変更はよくあるから REQ-06
    UC-06 利用者として、期限が近いタスクから順に見たい。なぜなら優先度の高いものを見落としたくないから REQ-07
    UC-07 利用者として、大きなタスクを小項目に分けて管理したい。なぜなら細かい進捗も追いたいから REQ-08
    UC-08 利用者として、チェックを入れるだけで完了リストに移動してほしい。なぜなら手動移動の手間を省きたいから REQ-09
    UC-09 利用者として、完了リストではいつ終わらせたかを確認したい。なぜなら自分の作業ペースを振り返りたいから REQ-10

    基本業務フロー

    1. 01

      タスク追加

      「未着手」リストにタスクを入力し、必要であれば期限を設定する

    2. 02

      進行中へ移動

      着手したタスクを「進行中」リストへドラッグする

    3. 03

      小項目でチェック

      タスクを分解した小項目を追加し、完了したものからチェックしていく

    4. 04

      完了チェック

      タスク全体が終わったら完了チェックボックスにチェックを入れる

    5. 05

      完了リストへ自動移動

      チェックと同時に「完了」リストへ自動で移動し、終了日が記録される

    6.機能要件

    MoSCoW方式で優先度を整理する。Mustは実装済み(v0.1)、Should/Couldは今後の対応候補。

    ID 要件 優先度 状態 受け入れ基準
    REQ-01 入力欄にテキストを入力し、カードを追加できる Must 実装済み 入力欄にテキストを入力して送信すると、「未着手」リストの末尾にカードが表示される。空文字では追加されない
    REQ-02 カードの「×」ボタンで削除できる Must 実装済み 削除ボタンを押すと、確認なしで即座にカードが一覧から消え、再読み込みしても復活しない
    REQ-03 カードをドラッグして別のリストへ移動できる Must 実装済み カードを別リストの枠内へドラッグ&ドロップすると、元のリストから消え、移動先リストの末尾に表示される
    REQ-04 データをlocalStorageに保存し、リロード後も保持する Must 実装済み カードの追加・編集・削除・移動のいずれかの操作後にページを再読み込みしても、直前の状態がそのまま復元される
    REQ-05 リストの追加・名称変更・削除ができる Should 未実装 「リスト追加」操作で新しい空リストが末尾に作成できる。既存リストの名称を変更でき、削除するとリスト内のカードごと一覧から消える(削除時は確認を挟む)
    REQ-06 カードのテキスト・期限をあとから編集できる Should 実装済み 編集ボタンでカードが編集フォームに切り替わり、保存すると新しいテキスト・期限が反映される。空文字では保存できない
    REQ-07 各リスト内でカードが期限の早い順に自動で並ぶ(期限なしは末尾) Should 実装済み 期限が設定されているカードは期限の昇順で並び、期限未設定のカードは末尾にまとめて表示される
    REQ-08 カードの中にチェックリスト(小項目)を追加・完了・削除できる Should 実装済み 小項目を入力して追加すると一覧に表示され、チェックで完了状態(取り消し線)になり、削除ボタンで一覧から消える
    REQ-09 未着手・進行中のカードにチェックを入れると、自動で完了リストへ移動する Should 実装済み 「未着手」「進行中」のカードで完了チェックボックスにチェックを入れると、即座に「完了」リストへ移動し、元のリストから消える
    REQ-10 完了リストでは期限の代わりに終了日(完了した日付)を表示する Should 実装済み 「完了」リストのカードには期限バッジの代わりに「終了日 ◯/◯」が表示され、完了した日付と一致する
    REQ-11 同一リスト内でカードを手動で並び替えられる Could 未実装 同一リスト内でカードをドラッグして任意の位置に挿入でき、その並び順が再読み込み後も保持される
    REQ-12 複数ボードを作成・切り替えできる Could 未実装 新規ボードを作成でき、ボード切り替え操作で表示されるカード一覧がボードごとに独立している(片方の操作がもう片方に影響しない)
    REQ-13 ユーザー登録・ログイン Won’t(今回) 対象外 対象外のため受け入れ基準なし
    REQ-14 サーバー(DB)にデータを保存し、複数端末から同じデータを参照・編集できる(認証なし・単一ユーザー想定) Should 未実装 ある端末でカードを追加・編集・削除・移動したあと、別端末で同じURLを開くと、その変更結果が反映されている

    7.非機能要件

    IPA非機能要求グレードの分類を参考に、6つの観点で整理する。

    可用性

    • 動作環境 サーバー不要。index.htmlをブラウザで開くだけで動作すること
    • データ永続性の範囲 同一ブラウザ・同一端末内でのみ保持される(localStorageの制約による)。サーバー障害による停止は起こり得ない構成とする

    性能・拡張性

    • パフォーマンス カード数十〜数百件程度で操作にもたつきがないこと
    • 拡張性 リストやボードの追加(REQ-05, REQ-12)など、今後の機能追加に耐えられるデータ構造とすること

    運用・保守性

    • 環境構築 npmなどのビルドツールに依存せず、HTML・CSS・JSのみで完結すること。導入コストをゼロに保つ
    • コードの可読性 1機能=1関数を基本とし、コメントなしでも処理内容が追える命名・構造にすること

    移行性(互換性)

    • 対応環境 最新版のChrome / Safari / Firefoxなど、モダンブラウザで動作すること
    • データ形式 localStorageに保存するデータはJSON形式とし、将来サーバー保存へ移行する際にそのまま流用できる構造にすること

    セキュリティ

    • 入力値の扱い カードのテキストはDOM APIで挿入し、HTMLとして解釈させない(XSS対策)。innerHTMLへのユーザー入力の直接挿入は行わない
    • アクセス制御 認証機能を持たないため、同じ端末・ブラウザを利用できる人は誰でも閲覧・編集できる(REQ-13は対象外のため、これはリスクとして許容する)

    ユーザビリティ

    • 操作性 マウス・トラックパッドでのドラッグ&ドロップに対応すること。キーボードのみでの操作は範囲外

    8.画面構成

    画面は単一ページで構成し、ヘッダーと3列のボードのみを持つシンプルな構造とする。

    header   h1 "タスクボード" main.board   section.list [未着手 / 進行中 / 完了]     h2     div.cards       div.card × N         due-badge (期限 or 終了日)         complete-checkbox (未着手・進行中のみ) + card-text         subtasks (進捗・チェックリスト・小項目追加フォーム)         edit-btn(✎) / delete-btn(×)     form.add-card-form       text入力 → due入力 → 追加ボタン

    各リストは同一構造(見出し・カード一覧・追加フォーム)を持ち、data-list-id属性でどのリストかを識別する。編集ボタンを押すとカードがその場で編集フォームに切り替わる。

    画面/状態遷移図

    現状は単一ページ内の状態切り替えのみだが、REQ-05・REQ-12の実装を見据え、将来の画面/状態も含めて整理する。

    ID 名称 説明
    SCR-01 ボード画面(通常表示) 3リストのカード一覧を表示する、現在実装済みのメイン画面
    SCR-02 カード編集モード 編集ボタン押下でカードがその場で編集フォームに切り替わる(実装済み)
    SCR-03 リスト編集モード(予定) REQ-05実装後、リストの追加・名称変更・削除を行う
    SCR-04 ボード一覧/切り替え画面(予定) REQ-12実装後、複数ボードを作成・切り替える

    9.データモデル

    状態は1つのオブジェクトで管理し、リストIDをキーにカードオブジェクトの配列を持つ。表示順は配列の順序ではなく、描画のたびに期限(due)の早い順で並び替えて決まる。

    {
  "todo": [
    {
      "text": "要件定義書を読む",
      "due": "2026-09-15",
      "subtasks": [
        { "text": "5章まで読む", "done": true },
        { "text": "コメントを書く", "done": false }
      ],
      "completedAt": ""
    }
  ],
  "doing": [
    { "text": "トレロ風アプリの実装", "due": "", "subtasks": [], "completedAt": "" }
  ],
  "done": [
    {
      "text": "ghコマンドのインストール",
      "due": "",
      "subtasks": [],
      "completedAt": "2026-09-11"
    }
  ]
}

    この状態は localStorage["trello-clone-data"] にJSON文字列として保存される。completedAtは「完了」リストに入った日付で、完了チェックまたはドラッグでの移動時に自動で設定される。

    拡張案(REQ-05 / REQ-11 / REQ-12 対応後)

    現状のモデルは「リストID(todo/doing/done)が固定」「カードが配列の位置でしか識別できない」という前提に依存しており、リストの追加・削除(REQ-05)や手動並び替え(REQ-11)、複数ボード(REQ-12)に対応できない。これらに対応するため、以下のようにモデルを拡張する案を示す。

    {
  "activeBoardId": "board-1",
  "boards": [
    {
      "id": "board-1",
      "name": "マイボード",
      "lists": [
        { "id": "todo", "name": "未着手", "order": 0 },
        { "id": "doing", "name": "進行中", "order": 1 },
        { "id": "done", "name": "完了", "order": 2 }
      ],
      "cards": [
        {
          "id": "card-a1b2c3",
          "listId": "todo",
          "order": 0,
          "text": "要件定義書を読む",
          "due": "2026-09-15",
          "subtasks": [
            { "text": "5章まで読む", "done": true }
          ],
          "completedAt": ""
        }
      ]
    }
  ]
}

    主な変更点は次の3つ。

    • boards 配列を追加し、ボードごとに lists と cards を持たせる(REQ-12)
    • リストを固定キーではなく lists 配列(id・name・order)として持たせ、追加・改名・削除を可能にする(REQ-05)
    • カードに一意な id と order を持たせ、配列の位置ではなくIDと並び順の値で識別・並び替えできるようにする(REQ-11)。現状のようにリストごとの配列に分けず、listId で所属リストを表す

    既存データ(v1形式)からの移行時は、todo/doing/done の3キーを lists 配列に変換し、各カードにUUID等で id を採番し、配列内の位置をそのまま order の初期値として引き継ぐ想定。

    10.バックエンド・API設計

    REQ-14(サーバー保存による複数端末同期)の対応にあたり、9章のデータモデル拡張案をもとにDBスキーマとAPIを設計する。具体的な実装言語・フレームワークは未定のため、本章では技術非依存の設計(テーブル定義・RESTエンドポイント)にとどめる。認証(REQ-13)は今回のスコープ外とし、単一ユーザーが利用する前提でユーザーテーブルは持たない。

    DBスキーマ(案)

    boards
  id            PK
  name          TEXT

lists
  id            PK
  board_id      FK -> boards.id
  name          TEXT
  order         INTEGER

cards
  id            PK
  list_id       FK -> lists.id
  text          TEXT
  due           DATE (nullable)
  completed_at  DATE (nullable)
  order         INTEGER

subtasks
  id            PK
  card_id       FK -> cards.id
  text          TEXT
  done          BOOLEAN

    9章のJSONモデルとほぼ1対1で対応する。boards → lists → cards → subtasks の順に親子関係を持ち、それぞれ外部キーで紐づく。

    APIエンドポイント(案)

    Method Path 説明
    GET/boardsボード一覧を取得する
    POST/boardsボードを新規作成する
    GET/boards/:boardId指定ボードのリスト・カード・小項目を含めて取得する
    POST/boards/:boardId/listsリストを追加する
    PATCH/lists/:listIdリスト名・並び順を変更する
    DELETE/lists/:listIdリストを削除する(配下のカードも削除)
    POST/lists/:listId/cardsカードを追加する
    PATCH/cards/:cardIdカードのテキスト・期限・所属リスト・並び順を更新する
    DELETE/cards/:cardIdカードを削除する
    POST/cards/:cardId/subtasks小項目を追加する
    PATCH/subtasks/:subtaskId小項目の完了状態・テキストを更新する
    DELETE/subtasks/:subtaskId小項目を削除する

    カードの移動(リスト間移動・並び替え)は個別のエンドポイントを設けず、PATCH /cards/:cardId で listId と order を更新する形に統一する。

    11.制約・前提

    • バックエンド・データベースを持たないため、ブラウザのデータを消去するとタスクも失われる
    • 認証機能がないため、同じ端末・ブラウザを使う人であれば誰でも閲覧・編集できる
    • 別のブラウザ・別の端末からは同じデータを参照できない

    12.リスクと対応策

    制約・前提から想定される主なリスクと、その対応策を整理する。

    ID リスク 影響度 対応策
    RISK-01 ブラウザのデータ削除やlocalStorageのクリアによるタスク全消失 高 REQ-14(サーバー/DB保存)への移行で根本的に解消される。移行までの間は定期的なエクスポート機能(JSONダウンロード)を検討する
    RISK-02 REQ-02のカード削除に確認ダイアログがなく、誤クリックで即削除される 中 削除前に確認ダイアログを挟む改修を検討する(現状は許容している既知のリスク)
    RISK-03 認証機能がないため、同じ端末・ブラウザを使える人なら誰でも閲覧・編集できる 低 個人利用が前提のため現状は許容する。共有端末で使う場合は利用者自身が注意する
    RISK-04 localStorageの保存容量上限(ブラウザ実装依存、目安5〜10MB)を超えると保存に失敗する可能性がある 低 想定利用件数(数十〜数百件)では上限に達しない見込み。上限に近づいた場合のエラーハンドリングは未対応
    RISK-05 フロントエンドのみの構成のため、コード変更ミスがアプリ全体の停止に直結する 中 Gitでバージョン管理し、問題発生時は直前のコミットに戻せる状態を保つ

    13.今後の拡張候補

    優先度が高いと考えられる順に、次の開発ステップの候補を挙げる。

    1. 01

      リストの編集機能(REQ-05)

      リストの追加・名称変更・削除に対応し、固定3列の制約をなくす。

    2. 02

      同一リスト内の手動並び替え(REQ-11)

      現在は期限順に自動で並ぶ仕様のため、同じ期限のカードや期限なしのカードを自由な順序でドラッグ並び替えできるようにする。

    3. 03

      複数ボードの管理(REQ-12)

      用途別にボードを分けて作成・切り替えできるようにする。

    4. 04

      バックエンド・DB化(REQ-14)

      10章のAPI・DBスキーマ設計をもとに、サーバー・DBを持つ構成へ移行する。技術スタックは未確定のため、選定から着手する。

    5. 05

      認証機能の追加(REQ-13)

      バックエンド化後、複数人での利用や公開を見据える場合にユーザー登録・ログインを追加する。

    14.KPI・成功指標

    本プロジェクトの目的(1章)は「ツールとしての完成度」よりも「要件定義 → 実装 → Gitでのバージョン管理」という開発の流れを身につけることにある。そのため、KPIも機能の完成度だけでなく、この開発プロセスをどれだけ実践できたかを中心に定義する。

    指標 目標・達成基準 測定方法
    機能要件の実装率 Must系は100%、Should系は80%以上を実装する 6章REQ表の状態(実装済み/未実装)を集計する
    受け入れ基準の充足確認 実装済みREQについて、対応する受け入れ基準を実際に操作して満たしていることを確認する 6章の受け入れ基準を1件ずつ手動でなぞり、結果を記録する
    要件定義書の改訂サイクル経験 実装内容に応じて要件定義書を複数回改訂し、コードとドキュメントを同期させる 15章の改訂履歴に記録されたバージョン数
    Gitでの意味のある単位のコミット 1コミットが1つの論理的な変更(1機能・1修正)に対応している git log でコミット単位と粒度を振り返る
    フロントエンドからバックエンドまでの到達度 10章で設計したAPI・DBスキーマを、実際にバックエンド実装まで到達させる(REQ-14) REQ-14のステータスが「実装済み」になっているか
    AIとの協働開発プロセスの実践 要件定義・設計・実装の各段階でAIを壁打ち相手として活用し、自分で意思決定する経験を積む 各章の内容について、AIの提案をそのまま採用せず、質問・修正を経て確定させた回数(定性的に振り返る)
