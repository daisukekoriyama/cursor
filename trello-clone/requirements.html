1.目的・背景

IT系講座の課題として、Trello風のタスク管理アプリを個人開発する。目的はツールとしての完成度そのものよりも、要件定義 → 実装 → Gitでのバージョン管理という一連の開発の流れを体験し、身につけることにある。

今回はすでに最小構成(MVP)のプロトタイプを先行して実装済み。本書はその実装内容を振り返って要件として言語化し、今後の拡張の土台とするために作成する。

2.スコープ

初回リリース(v0.1)で対応する範囲と、あえて対応しない範囲を明確にする。

対応する

  • 3つの固定リスト(未着手/進行中/完了)でのタスク管理
  • カードの追加・削除
  • ドラッグ&ドロップによるリスト間移動
  • ブラウザ内へのデータ保存(localStorage)

対応しない(今回)

  • ユーザー登録・ログイン
  • サーバーへの保存・複数端末同期
  • 複数ボードの作成
  • リストの追加・編集

3.用語定義

  • ボード
    タスク管理画面全体を指す最上位の単位。今回は1つのボードのみ存在する。
  • リスト
    進捗ステータスごとの列。「未着手」「進行中」「完了」の3種で固定。
  • カード
    1件のタスクを表す最小単位。テキストのみを持ち、いずれか1つのリストに属する。

    • 4.対象ユーザー

    作成者本人による、個人の学習・日々のタスク管理での利用を想定する。チームでの共有や複数人での同時利用は想定しない。

    5.機能要件

    MoSCoW方式で優先度を整理する。Mustは実装済み(v0.1)、Should/Couldは今後の対応候補。

    ID 要件 優先度 状態
    REQ-01 入力欄にテキストを入力し、カードを追加できる Must 実装済み
    REQ-02 カードの「×」ボタンで削除できる Must 実装済み
    REQ-03 カードをドラッグして別のリストへ移動できる Must 実装済み
    REQ-04 データをlocalStorageに保存し、リロード後も保持する Must 実装済み
    REQ-05 リストの追加・名称変更・削除ができる Should 未実装
    REQ-06 カードの内容編集・期限・メモを追加できる Should 未実装
    REQ-07 同一リスト内でカードを並び替えられる Could 未実装
    REQ-08 複数ボードを作成・切り替えできる Could 未実装
    REQ-09 ユーザー登録・ログイン Won’t(今回) 対象外
    REQ-10 サーバー保存による複数端末同期 Won’t(今回) 対象外

    6.非機能要件

    • 対応環境 最新版のChrome / Safari / Firefoxなど、モダンブラウザで動作すること
    • 環境構築 サーバー不要。index.htmlをブラウザで開くだけで動作すること
    • パフォーマンス カード数十〜数百件程度で操作にもたつきがないこと
    • データ永続性の範囲 同一ブラウザ・同一端末内でのみ保持される(localStorageの制約による)
    • 操作性 マウス・トラックパッドでのドラッグ&ドロップに対応すること。キーボードのみでの操作は範囲外

    7.画面構成

    画面は単一ページで構成し、ヘッダーと3列のボードのみを持つシンプルな構造とする。

    header   h1 "タスクボード" main.board   section.list [未着手]     h2, div.cards, form.add-card-form   section.list [進行中]     h2, div.cards, form.add-card-form   section.list [完了]     h2, div.cards, form.add-card-form

    各リストは同一構造(見出し・カード一覧・追加フォーム)を持ち、data-list-id属性でどのリストかを識別する。

    8.データモデル

    状態は1つのオブジェクトで管理し、リストIDをキーにカード文字列の配列を持つ。配列内の順序がそのまま表示順になる。

    {
  "todo":  ["要件定義書を読む", "GitHubにpushする"],
  "doing": ["トレロ風アプリの実装"],
  "done":  ["ghコマンドのインストール", "gh auth loginの設定"]
}

    この状態は localStorage["trello-clone-data"] にJSON文字列として保存される。

    9.制約・前提

    • バックエンド・データベースを持たないため、ブラウザのデータを消去するとタスクも失われる
    • 認証機能がないため、同じ端末・ブラウザを使う人であれば誰でも閲覧・編集できる
    • 別のブラウザ・別の端末からは同じデータを参照できない

    10.今後の拡張候補

    優先度が高いと考えられる順に、次の開発ステップの候補を挙げる。

    1. 01

      リストの編集機能(REQ-05)

      リストの追加・名称変更・削除に対応し、固定3列の制約をなくす。

    2. 02

      カード編集機能(REQ-06)

      カード内容の編集、期限・メモの追加に対応する。

    3. 03

      同一リスト内の並び替え(REQ-07)

      リスト内でのカードの順序をドラッグで変更できるようにする。

    4. 04

      バックエンド化の検討

      複数端末での同期や共有が必要になった場合、サーバー・DBを持つ構成へ移行する。
